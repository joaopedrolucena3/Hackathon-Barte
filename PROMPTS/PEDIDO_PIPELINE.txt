## Princípio: nenhuma chamada de LLM no workflow

Decisão do time: *o workflow não chama API de LLM*. Todo passo é código Python
determinístico. A mesma entrada gera sempre a mesma saída, byte a byte. Isso
sustenta B6 (auditabilidade) e o requisito do ⁠ 00_LEIA-ME.md ⁠: rodar de novo em
outubro com arquivos novos no mesmo formato.

Consequências práticas:

•⁠  ⁠Regras de negócio ficam em código e em configuração (parâmetros dos passos),
  nunca em prompts.
•⁠  ⁠O que o código não consegue decidir vira *exceção* para revisão humana (B5).
  O agente não chuta.
•⁠  ⁠Regras ainda não confirmadas pelo financeiro da Tarvo ficam registradas em
  ⁠ HIPOTESES.md ⁠ e parametrizadas, para trocar sem mexer em código.

## Stack sugerida

•⁠  ⁠Python 3.11+, *FastAPI* (API REST + SSE), *pandas* (transformações).
•⁠  ⁠⁠ openpyxl ⁠ para XLSX, ⁠ email ⁠ (stdlib) para o ⁠ .eml ⁠, parser OFX próprio ou
  ⁠ ofxparse ⁠ (o arquivo é OFX 1.02 SGML, charset 1252).
•⁠  ⁠Persistência: *SQLite* (um arquivo, zero setup) para runs, checklist, auditoria.
  Saídas de cada passo em *Parquet* em ⁠ saida/runs/<run_id>/ ⁠.
•⁠  ⁠Execução: uma ⁠ BackgroundTask ⁠ / thread por run. Volume é pequeno (~2 mil
  transações), não precisa de fila.

Estrutura proposta em ⁠ src/ ⁠:


src/
  api/            # FastAPI: rotas, schemas Pydantic, SSE
  pipeline/
    engine.py     # executa a definição, gerencia estado e eventos
    registry.py   # catálogo de passos (C1)
    steps/        # um módulo por passo
  readers/        # um leitor por formato de arquivo
  audit/          # trilha de auditoria e hashes
  config/         # parâmetros, mapeamentos, pipeline padrão (JSON)

## Modelo do pipeline (C1, B1)

### Catálogo de passos

Cada passo é uma classe registrada no ⁠ registry.py ⁠:

⁠ python
class Step(Protocol):
    type: str                 # "normalizar_orbe", "conferir_mdr", ...
    title: str                # texto curto para a lateral (B1)
    description: str          # o que faz, em português, para o contador
    inputs: list[str]         # ids de datasets que consome
    outputs: list[str]        # ids de datasets que produz
    params_schema: dict       # JSON Schema dos parâmetros editáveis no construtor
    version: str              # muda quando o código do passo muda (B6)

    def run(self, ctx: RunContext, params: dict) -> StepResult: ...
 ⁠

⁠ StepResult ⁠ traz: datasets produzidos, métricas (linhas in/out, totais em R$),
lista de *exceções* e mensagens de log.

### Definição de pipeline

JSON versionado, editado pelo construtor (C1) no front:

⁠ json
{
  "id": "fechamento-tarvo",
  "version": 3,
  "steps": [
    {"id": "s1", "type": "ler_arquivos", "params": {}},
    {"id": "s2", "type": "normalizar_orbe", "params": {}},
    {"id": "s3", "type": "resolver_lojista", "params": {"fallback": "cnpj"}},
    {"id": "s4", "type": "conferir_mdr", "params": {"tolerancia_pp": 0.0001}},
    {"id": "s5", "type": "vincular_estornos", "params": {}},
    {"id": "s6", "type": "conciliar_aurora", "params": {"janela_dias": 2}},
    {"id": "s7", "type": "processar_cambio", "params": {"participacao_spread": 0.5}},
    {"id": "s8", "type": "gerar_lancamentos", "params": {}},
    {"id": "s9", "type": "aprovacao", "params": {}},
    {"id": "s10", "type": "exportar_erp", "params": {"formato": "csv_fenix"}}
  ]
}
 ⁠

Regras de validação ao salvar (retornar 422 com a lista de erros):

•⁠  ⁠Todo ⁠ type ⁠ existe no catálogo; ⁠ params ⁠ valida contra ⁠ params_schema ⁠.
•⁠  ⁠A ordem respeita dependências: cada ⁠ input ⁠ de um passo foi produzido antes.
•⁠  ⁠Existe exatamente um passo ⁠ aprovacao ⁠ e ele vem *antes* de ⁠ exportar_erp ⁠
  (B5 não pode ser removido nem movido para depois da exportação).
•⁠  ⁠Salvar cria nova ⁠ version ⁠; versões antigas nunca são sobrescritas (B6).

### Passos do pipeline padrão

As regras marcadas *[H]* são hipóteses a confirmar com o financeiro da Tarvo e
devem estar em ⁠ HIPOTESES.md ⁠.

 1.⁠ ⁠*Ler arquivos* — roda os 6 leitores. Falha dura se algum arquivo faltar ou
   não abrir. Saída: datasets brutos.
 2.⁠ ⁠*Normalizar Orbe* — datas, decimais, nome do lojista canônico por
   ⁠ cod_estabelecimento ⁠, faixa de parcelas (⁠ 1 ⁠ → crédito à vista, ⁠ 2–6 ⁠,
   ⁠ 7–12 ⁠). Exceção: linha com campos obrigatórios vazios.
 3.⁠ ⁠*Resolver lojista* — liga Orbe ↔️ tabela de taxas por "EC Orbe"; sem EC,
   tenta CNPJ normalizado (14 dígitos com zero à esquerda) e por fim nome
   normalizado (sem acento, sem LTDA, maiúsculas). Match só por nome = exceção
   "vínculo fraco" para revisão. Atenção a nomes parecidos e distintos
   (⁠ HORIZONTE VIAGENS TURISMO ⁠ ≠ ⁠ HORIZONTE INTERCAMBIO ⁠).
 4.⁠ ⁠*Conferir MDR* — para cada VENDA, escolhe a taxa contratada **vigente na
   data da venda** (Bridge muda em 15/09) pela modalidade/faixa e compara com
   ⁠ taxa_aplicada_pct ⁠. Calcula ⁠ diferenca_pp ⁠ e ⁠ impacto_rs ⁠. Exceções:
   divergência acima da tolerância, lojista inativo com venda, lojista sem taxa
   para a modalidade. *[H]* taxa da ANTECIPACAO comparada com a coluna
   "Antecipação".
 5.⁠ ⁠*Vincular estornos* — liga ESTORNO e REVERSAO ANTECIPACAO à operação
   original por ⁠ id_referencia ⁠. Exceções: referência inexistente no mês,
   estorno maior que a venda, estorno duplicado.
 6.⁠ ⁠*Conciliar Aurora* — *[H]* soma do ⁠ valor_liquido ⁠ da Orbe por data de
   liquidação ↔️ TEDs ⁠ ORBE ADQUIRENCIA ⁠ no extrato; PIX enviados ↔️ repasses a
   lojistas. Casamento por valor exato e janela de datas (⁠ janela_dias ⁠).
   Exceções: TED sem par, diferença de valor, PIX para lojista não identificado.
   Tarifas, folha, condomínio e transferência entre contas são classificados por
   regra de texto do histórico.
 7.⁠ ⁠*Processar câmbio* — lê o anexo da Ponte Câmbio e o OFX Meridiano.
   Receita = ⁠ participacao_spread ⁠ (50%, do corpo do e-mail) × spread realizado.
   *[H]* spread contratado por lojista vem da coluna "Spread remessa"; vazio ou
   ⁠ padrão ⁠ usa o valor padrão (desconhecido; parâmetro obrigatório). Operações
   "APROVADO C/ RESSALVA" entram como liquidadas, mas são sinalizadas.
 8.⁠ ⁠*Gerar lançamentos* — monta partidas dobradas usando só contas analíticas do
   plano Fênix (ex.: ⁠ 1.1.01.001 ⁠ Banco Aurora, ⁠ 1.1.03.001 ⁠ Recebíveis Orbe,
   ⁠ 3.1.01 ⁠ Receita de MDR, ⁠ 3.1.02 ⁠ Receita de antecipação, ⁠ 3.1.03 ⁠ Receita de
   intermediação de câmbio, ⁠ 4.2.01 ⁠ Tarifas bancárias,
   ⁠ 1.1.09.002 ⁠ Créditos não identificados). *[H]* o mapeamento evento → contas
   fica em ⁠ config/mapa_contabil.json ⁠. Exceções: conta inexistente ou sintética,
   lote desbalanceado (débito ≠ crédito).
 9.⁠ ⁠*Aprovação* (B5) — passo especial: não calcula nada; muda o run para
   ⁠ awaiting_approval ⁠ e espera a decisão.
10.⁠ ⁠*Exportar ERP* — só roda com run ⁠ approved ⁠. Grava
    ⁠ saida/<competencia>/lancamentos_fenix.csv ⁠ + ⁠ relatorio_excecoes.csv ⁠ +
    ⁠ auditoria.json ⁠.

## Execução (B3, B4)

### Estados do run


queued → running → awaiting_approval → approved → exporting → done
                 ↘️ failed              ↘️ rejected


•⁠  ⁠⁠ failed ⁠: erro não tratado em um passo. Guarda traceback no audit; passos
  seguintes ficam ⁠ skipped ⁠.
•⁠  ⁠⁠ rejected ⁠: revisor reprovou. Nada é exportado. O run fica arquivado; o próximo
  run é um run novo (nunca "editar" um run).
•⁠  ⁠Estado por passo: ⁠ pending | running | done | done_with_exceptions | failed | skipped ⁠.

### Disparo com um clique

⁠ POST /api/runs ⁠ com competência e (opcional) arquivos enviados. Sem upload, usa
⁠ Tarvo_Data_Pack_<competencia>/ ⁠. Valida a competência (⁠ AAAA-MM ⁠) e se já existe
run ⁠ running ⁠ para ela (409).

### Eventos em tempo real

⁠ GET /api/runs/{id}/events ⁠ via *Server-Sent Events*. Tipos de evento:

⁠ json
{"type": "run_started",   "run_id": "...", "at": "..."}
{"type": "step_started",  "step_id": "s4", "at": "..."}
{"type": "step_progress", "step_id": "s4", "done": 800, "total": 1943}
{"type": "step_finished", "step_id": "s4", "status": "done_with_exceptions",
 "metrics": {"rows_in": 1943, "rows_out": 1943, "exceptions": 37}, "duration_ms": 412}
{"type": "awaiting_approval", "exceptions_open": 52}
{"type": "run_finished",  "status": "done"}
 ⁠

Cada evento também é gravado; ⁠ GET /api/runs/{id} ⁠ devolve o estado consolidado
para o front se reconectar sem perder nada.

## Aprovação humana (B5)

•⁠  ⁠Ao chegar no passo ⁠ aprovacao ⁠, o backend consolida todas as exceções do run
  com: ⁠ id ⁠, ⁠ step_id ⁠, ⁠ tipo ⁠, ⁠ severidade ⁠ (⁠ bloqueante | alerta ⁠), descrição,
  referência à(s) linha(s) de origem, ⁠ impacto_rs ⁠.
•⁠  ⁠Revisor pode, por exceção: *aceitar* (segue), *ajustar* (informa valor/conta
  corretos, com justificativa obrigatória) ou *excluir do lote*.
•⁠  ⁠Aprovação final só é aceita se não houver exceção ⁠ bloqueante ⁠ aberta (422).
•⁠  ⁠Toda decisão grava ⁠ quem ⁠, ⁠ quando ⁠, ⁠ antes ⁠, ⁠ depois ⁠, ⁠ justificativa ⁠.
•⁠  ⁠Ajustes não reescrevem a saída dos passos anteriores: geram um dataset
  ⁠ ajustes ⁠ aplicado no passo de exportação (rastreável).

## Auditabilidade (B6)

Cada run grava em ⁠ audit ⁠ (SQLite) e exporta em ⁠ auditoria.json ⁠:

•⁠  ⁠Arquivos de entrada: nome, SHA-256, tamanho, linhas lidas/descartadas.
•⁠  ⁠Definição do pipeline usada (⁠ id ⁠ + ⁠ version ⁠) e ⁠ version ⁠ de cada passo.
•⁠  ⁠Para cada passo: início, fim, duração, parâmetros efetivos, métricas, hash do
  dataset de saída, exceções geradas.
•⁠  ⁠Decisões de aprovação (acima) e o arquivo exportado com seu hash.
•⁠  ⁠Commit do git do código (⁠ git rev-parse HEAD ⁠) se disponível.

*Teste de reprodutibilidade:* rodar duas vezes com os mesmos arquivos e a mesma
versão do pipeline tem que produzir hashes de saída idênticos. Vale um teste
automatizado e é um ótimo momento da demo.

## Preview de dados (C8)

•⁠  ⁠Saída de cada passo salva em Parquet; preview lê dali (não reprocessa).
•⁠  ⁠Paginação no servidor (⁠ page ⁠, ⁠ page_size ⁠ ≤ 500), ordenação e filtro simples
  por coluna (⁠ eq ⁠, ⁠ contains ⁠, ⁠ gt ⁠, ⁠ lt ⁠) e ⁠ only_exceptions=true ⁠.
•⁠  ⁠A resposta inclui o *schema* com metadado por coluna: tipo (⁠ money ⁠,
  ⁠ percent ⁠, ⁠ date ⁠, ⁠ text ⁠), e se é coluna *nova* neste passo (o front destaca).
•⁠  ⁠Linhas com exceção trazem ⁠ __exception_ids ⁠ para o front marcar e linkar.
•⁠  ⁠⁠ diff=true ⁠ compara com o dataset de entrada do passo (linhas
  adicionadas/removidas, colunas novas).

•⁠  ⁠Leitores: cada armadilha da tabela de entrada vira um teste (percentual em
